# SwiftProof v0.3.0

This release lets the deployment, rather than the reviewed repository, decide
which provider the reviewer talks to: the endpoint and model arrive as
environment variables and the API key as a mounted Docker secret. The trusted
baseline policy keeps deciding everything else, and `.swiftproof.json` gains no
new key.

## Included

- `SWIFTPROOF_REVIEWER_ENDPOINT` and `SWIFTPROOF_REVIEWER_MODEL` override
  `reviewer.endpoint` and `reviewer.model` for the run. The same URL rules apply:
  HTTPS remotely, HTTP only on loopback, no credentials, query or fragment.
- The API key is taken from the variable named by `reviewer.api_key_env`
  (`SWIFTPROOF_API_KEY` by default), then from the file named by `<NAME>_FILE`,
  then from the Docker secret mounted at `/run/secrets/<NAME>`. A variable
  present in the environment wins, which is the order the surrounding Swarm
  deployment uses.
- The key file is read whole with surrounding whitespace stripped, so a secret
  created with a trailing newline works unchanged. It is bounded to 8 KiB and
  must be a single line.
- A key file named explicitly by `<NAME>_FILE`, and any mounted key file that
  cannot be used, fail the run with exit 3 instead of silently sending an
  unauthenticated request. The conventional `/run/secrets/<NAME>` simply being
  absent is not an error.
- A blank variable counts as unset, so an exported-but-empty value in a compose
  file cannot silently replace a value configured in policy.
- A model supplied by the environment enables `review` exactly as a policy model
  does. `--reviewer=false` still disables provider calls, and `lint` still never
  calls a provider.
- When the reviewer runs, the run log names each value's source — the variable or
  file name, never the credential.
- `reviewer.api_key_env` may now be empty, which disables the credential entirely
  for a local provider that takes none.

## Upgrading

Nothing to change. Existing shell and CI setups that export `SWIFTPROOF_API_KEY`
keep working, because the variable is still the first source, and a policy that
configures the endpoint and model keeps working when no variable is set.

Unlike v0.2.0's `coverage` key, this release adds **no** configuration key: a
policy written for v0.1.0 or v0.2.0 is accepted unchanged, and older pinned
binaries accept a policy written for this release. Only the binary that performs
the review needs to be v0.3.0 for the environment and the secret to be read.

Whoever can set the process environment chooses where redacted source context is
sent, so it is a trusted input at the same level as the pinned binary. Keep these
variables and the mounted secret out of any job that runs untrusted fork code;
candidate commits and pull request branches never reach them. Image, commands,
budgets and sensitive paths remain policy-only decisions. See
[security boundaries](../SECURITY.md) and [CI integration](../CI.md).

## Installation

Download the archive for your operating system and architecture, verify its entry
in `SHA256SUMS`, extract it, and put `swiftproof` (`swiftproof.exe` on Windows) on
your PATH. Run `swiftproof version` to verify installation.

Git is required. Docker with Linux containers and a preloaded toolchain image is
required only for executing repository checks, including the coverage run. Go is
not required to run the downloaded CLI.

## Current limits

The environment supplies the endpoint, the model and the credential, and nothing
else: there is no variable for the sandbox image, the commands, the budgets or the
sensitive paths, and there is no way for a candidate change to set any of them.
The credential is never written to a report, but masking of secrets found in
repository content remains best effort.

This remains a 0.x release: signals and passing checks are not a correctness
guarantee and never automatically approve or merge a pull request. Archives are
not signed or notarized. See README.md and SECURITY.md for setup and execution
boundaries.
