# SwiftProof v0.4.0

This release records more deterministic evidence and depends less on a model.
Changed and existing tests, and changed functions, can run on both revisions
without a model; recorded values can be compared instead of model-written
assertions; and exports contain only findings backed by recorded evidence. None
of the new records produces exit 1: only a reproduced high/critical hypothesis
does. The binding rules are in the
[v0.4 specification](../../../specs/swiftproof-v0.4-spec.md).

## Included

- `--deadline D` (from 1m to 24h) bounds dependency preparation, sandbox runs
  and the reviewer, and keeps 30 s to clean up and write the report. Running
  containers end as TIMEOUT, unstarted runs are recorded as SKIPPED, and the
  report records the deadline as an unverified area.
- One shared runtime budget: each sandbox run reserves its timeout before it
  starts, the new stages have sub-caps inside `sandbox.max_runtime_seconds`, and
  half of the budget is reserved for the reviewer's experiments when a reviewer
  runs. Dependency preparation has its own timeout instead.
- A single `divergences` list and an always-present **Behavior Divergences**
  section, shared by observation experiments and differential fuzzing. Each
  entry shows both recorded values and states that it does not establish which
  revision is correct.
- A reviewer call to a tool outside the offered set is audited as
  `rejected_tool_call`, and harness stages are audited under the reserved
  `stage:` prefix, so a model cannot write audit entries that look like
  harness stages.

## Upgrading

**Upgrade in this order.** A pipeline pinned to v0.3.0 or earlier breaks the
moment a new key lands in its base-branch policy or a new flag is passed to it.

1. Publish v0.4.0, together with the updated report schema.
2. Re-pin every workflow that reviews your base branch to v0.4.0, updating the
   download URL and the pinned sha256 together (for example in your copy of
   `.github/workflows/review.yml`).
3. Only then commit a `fuzz`, `mutation` or `prepare` object to a base-branch
   policy, or pass a new flag: `--base-tests`, `--fuzz`, `--impact`,
   `--impacted-tests`, `--cache-dir`, `--parallel`, `--allow-prepare-network`,
   `--deadline`, `--report-url`, or `--format` with `sarif` or `pr-comment`.

A policy containing `fuzz`, `mutation` or `prepare` is **rejected with exit 3 by
every earlier binary**, because policy decoding refuses unknown fields, and each
new flag makes an earlier binary exit 3 while parsing arguments. `swiftproof init`
never writes the new keys. An earlier binary's `swiftproof report` silently drops
the new report fields and shows hypothesis statuses it does not know as
`UNVERIFIED`, so render reports with v0.4.0. Consumers that validate reports
against the v0.3 schema reject v0.4 reports; update the schema first. See
[CI integration](../CI.md).

Without any new key or flag, v0.4.0 still changes its output:

- JSON reports always contain the `intent_criteria`, `divergences` and
  `intent_test_failures` arrays, possibly empty, and lint and review reports
  contain an `impact` object unless `--impact=false` is passed.
- The Markdown report always contains a Behavior Divergences section.
- The initial checks are announced on one progress line, for example
  "Running test, typecheck, build in isolated Docker sandboxes...".
- The reviewer is offered a `find_callers` tool and may claim the `DIVERGED`
  status, which `Finalize` accepts only with validated observation or fuzz
  evidence.
- Every string kept from a Jest-compatible report is now redacted, and a report
  whose normalized results would still change under redaction is rejected as
  unreadable, which records its check as ERROR.
- Under `--ci`, a configured `fuzz` or `mutation` stage, or a requested
  `--base-tests` or `--impacted-tests` run, that did not run requests human
  review (exit 2).

## Installation

Download the archive for your operating system and architecture, verify its entry
in `SHA256SUMS`, extract it, and put `swiftproof` (`swiftproof.exe` on Windows) on
your PATH. Run `swiftproof version` to verify installation.

Git is required. Docker with Linux containers is required only for executing
repository code, including dependency preparation. Go is not required to run the
downloaded CLI.

## Current limits

Behavior divergences, tests that fail on candidate code, intent-test failures and
surviving mutants ask for human judgment. None of them establishes which revision
is right, and none produces exit 1. SwiftProof makes no equivalence,
completeness or mutation-score claim, and a report with no finding is not an
approval.

This remains a 0.x release: signals and passing checks are not a correctness
guarantee and never automatically approve or merge a pull request. Archives are
not signed or notarized. See README.md and SECURITY.md for setup and execution
boundaries.
