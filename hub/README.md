# SwiftProof Hub

The web application that complements the SwiftProof CLI: sign in with GitHub or
GitLab, get a `.swiftproof.json` policy created for the repositories that have
none, and read an evidence-backed report for every new commit.

It is a single Go binary with an embedded UI, no database and no external
service, packaged as one container so a company can run it internally next to
its GitHub Enterprise or GitLab instance.

## What it does

| Step | Behaviour |
| --- | --- |
| **Sign in** | OAuth with GitHub (github.com or GHES) or GitLab (gitlab.com or self-managed). The access token is sealed with AES-GCM before it touches the disk. |
| **Bootstrap** | Every repository without `.swiftproof.json` on its default branch gets a one-click proposal. The policy is generated by the CLI shipped in the image — previewed first, then committed on the default branch. |
| **Monitor** | Repositories that have a policy can be watched: the hub installs a push webhook with a per-repository secret and a random, non-enumerable routing URL. |
| **Report** | Each new commit is analyzed and its report opens in the dashboard on its own, over a live event stream. |
| **Filter** | A severity slider (low → medium → high → critical) filters the alert list live; clicking an alert unfolds every modification it concerns, with the flagged lines highlighted in the diff. |
| **Trace** | Commit statuses on the forge, an SVG badge for a README, the per-commit history, and the untouched JSON report for download. |

A report states what was observed and what was reproduced. The hub never
approves a change and never turns a zero exit code into a claim of correctness.

## Analysis modes

* `lint` (default) — maps the diff to risk signals. It **never executes
  repository code**, so it is safe to point at untrusted repositories.
* `review` — also runs the configured checks in the CLI's Docker sandbox and
  tries to reproduce issues with differential tests. It needs a Docker socket,
  which the operator must mount deliberately, and inherits the CLI's isolation
  (non-root, no network, read-only mounts, preloaded images only).

The LLM investigation stays a deployment decision: the hub holds no provider
credential and only forwards `SWIFTPROOF_REVIEWER_ENDPOINT`,
`SWIFTPROOF_REVIEWER_MODEL` and `SWIFTPROOF_API_KEY` to the CLI when they are
set on the container.

## Run it

```sh
docker build -f hub/Dockerfile -t swiftproof-hub .

docker run --rm -p 8080:8080 \
  -e SWIFTPROOF_HUB_BASE_URL=https://swiftproof.example.com \
  -e SWIFTPROOF_HUB_GITHUB_CLIENT_ID=... \
  -e SWIFTPROOF_HUB_GITHUB_CLIENT_SECRET=... \
  -v swiftproof-hub-data:/var/lib/swiftproof-hub \
  swiftproof-hub
```

The published image is `gvinsot/swiftproof-hub` on Docker Hub; the post-build
script below also targets an internal registry.

### OAuth application

Register one application per forge, with these URLs:

| Forge | Callback URL | Scopes |
| --- | --- | --- |
| GitHub | `<BASE_URL>/auth/github/callback` | `repo`, `read:org` |
| GitLab | `<BASE_URL>/auth/gitlab/callback` | `api` |

`BASE_URL` must be the public URL of the deployment: the forge posts its
webhooks there.

### Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `SWIFTPROOF_HUB_BASE_URL` | — | **Required.** Public URL of this deployment. |
| `SWIFTPROOF_HUB_ADDR` | `:8080` | Listen address. |
| `SWIFTPROOF_HUB_DATA_DIR` | `/var/lib/swiftproof-hub` | State directory; back it up. |
| `SWIFTPROOF_HUB_SESSION_KEY` | generated | 64 hex characters. Seals sessions and stored tokens; set it explicitly to run several replicas. |
| `SWIFTPROOF_HUB_MODE` | `lint` | `lint` or `review`. |
| `SWIFTPROOF_HUB_WORKERS` | `2` | Concurrent analyses. |
| `SWIFTPROOF_HUB_QUEUE_SIZE` | `256` | Pending analyses before webhooks are asked to retry. |
| `SWIFTPROOF_HUB_ANALYSIS_TIMEOUT` | `10m` | Hard limit per analysis. |
| `SWIFTPROOF_HUB_CLONE_DEPTH` | `50` | Shallow fetch depth. |
| `SWIFTPROOF_HUB_MAX_REPOS` | `500` | Repositories listed per account. |
| `SWIFTPROOF_HUB_SESSION_TTL` | `12h` | Session lifetime. |
| `SWIFTPROOF_HUB_COMMIT_STATUS` | `true` | Publish the verdict on the analyzed commit. |
| `SWIFTPROOF_HUB_DEFAULT_BRANCH_ONLY` | `false` | Analyze only pushes to the default branch. |
| `SWIFTPROOF_HUB_LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error`. |
| `SWIFTPROOF_HUB_GITHUB_CLIENT_ID` / `_SECRET` | — | GitHub OAuth application. |
| `SWIFTPROOF_HUB_GITHUB_URL` / `_API_URL` | github.com | Point these at a GitHub Enterprise Server host (`https://ghe.internal`, `https://ghe.internal/api/v3`). |
| `SWIFTPROOF_HUB_GITLAB_CLIENT_ID` / `_SECRET` | — | GitLab OAuth application. |
| `SWIFTPROOF_HUB_GITLAB_URL` | gitlab.com | Self-managed GitLab base URL. |

Any `*_SECRET` may also be supplied as `<NAME>_FILE` or through
`/run/secrets/<NAME>`, following the Docker secret convention the CLI uses.

## Publishing the image

`hub/scripts/postbuild.sh` builds, tags and pushes the image. It runs after the
build in CI and can be run by hand:

```sh
# Docker Hub, credentials from the environment
DOCKERHUB_USERNAME=... DOCKERHUB_TOKEN=... VERSION=v0.4.0 hub/scripts/postbuild.sh

# Internal registry, no Docker Hub involved
REGISTRY=registry.internal IMAGE_NAMESPACE=platform hub/scripts/postbuild.sh

# Build and tag only
PUSH=false hub/scripts/postbuild.sh
```

Only a `vX.Y.Z` version moves the `latest` tag; a development build never does.

In CI, the workflow in
[`devops/github-workflows/hub.yml`](../devops/github-workflows/hub.yml) tests
the module, then runs this script as its post-build step. Copy it to
`.github/workflows/hub.yml` to activate it, and set the `DOCKERHUB_USERNAME`
and `DOCKERHUB_TOKEN` repository secrets; without them the workflow still
builds and smoke-tests the image, it just does not publish.

## Security model

* **Sessions** are signed cookies (HTTP-only, `SameSite=Lax`, `Secure` behind
  HTTPS) that carry no credential — the sealed token stays server-side.
* **CSRF**: every state-changing call needs a session-bound token in the
  `X-SwiftProof-CSRF` header, and a same-origin check.
* **Webhooks** are authenticated with a per-repository secret — HMAC-SHA256 for
  GitHub, a constant-time token comparison for GitLab — on an unguessable
  routing URL, and the payload's repository identity is matched before anything
  is queued.
* **Git credentials** are passed to `git` through scoped `GIT_CONFIG_*`
  variables, never on a command line and never to another host.
* **Isolation between accounts**: every read and write is scoped to the session
  owner; a repository key from another account resolves to 404.
* **The UI ships no inline script**, so the service serves a strict
  `Content-Security-Policy` without `unsafe-inline`.
* **The analyzed code is never executed in `lint` mode.**

## Endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/healthz` | Liveness, CLI version, queue depth. |
| `GET` | `/auth/{github,gitlab}/start` · `/callback` | OAuth flow. |
| `GET` | `/api/me` | Session, configured forges, CSRF token. |
| `GET` `POST` | `/api/repos` · `/api/repos/sync` | List and refresh repositories. |
| `POST` | `/api/repos/{repo}/policy` | Preview (`{"preview":true}`) or commit `.swiftproof.json`. |
| `POST` `DELETE` | `/api/repos/{repo}/monitor` | Install or remove the push webhook. |
| `POST` | `/api/repos/{repo}/analyze` | Analyze a commit, or the tip of the default branch. |
| `GET` | `/api/repos/{repo}/runs` | Report history. |
| `GET` | `/api/repos/{repo}/reports/{commit}` · `/raw` | Rendered view, or the stored JSON report. |
| `GET` | `/api/events` | Server-sent analysis updates of the signed-in account. |
| `POST` | `/hooks/{key}` | Webhook receiver. |
| `GET` | `/badge/{key}.svg` | Latest verdict as a badge. |

## Development

```sh
go test ./hub/...          # from the repository root, through go.work
go vet ./hub/...
```

The UI lives in `hub/web/public/` and is embedded at build time; editing it
needs no toolchain. Reports are decoded against the published
[confidence report schema](../app/schema/confidence-report.schema.json), and
unknown fields are ignored so a newer CLI cannot break the dashboard.
